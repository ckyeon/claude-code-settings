# 0120 — herdr agent 여럿을 함께 운영하는 절차를 herdr-fleet skill로 둔다

직접 작성한 skill `user/shared/skills/herdr-fleet/`을 더했다. 한 세션이 herdr agent를 셋 넘게 띄울 때 쓰고, 조정자가 board, 상태 파일, digest, 정기 보고로 fleet을 운영하게 한다. skill-creator dry-run을 세 번 돌려 skill이 있을 때와 없을 때를 비교했고, 그 결과로 절마다 남길지 정했다.

## 경위

- 다른 프로젝트 세션이 inbox에 남긴 건의 둘(ADR 0098, ADR 0119)에서 왔다. 그 세션은 하루 동안 herdr agent 15개를 띄워 운영했다. 그 과정에서 다음 문제가 났다.
  - 진척을 한눈에 볼 곳이 없어서 조정 세션이 agent마다 보고 파일을 따로 열어 읽었다.
  - 알림이 사건마다 와서 조정 세션이 알림 하나에 한 turn씩 썼다.
  - 사용자는 무슨 문제를 풀고 있고 잘 풀고 있는지 중간에 확인하지 못했다.
  - agent 여럿이 쓴 결과가 검수 없이 운영 서버로 나갔다.
- `skills/herdr`는 agent 하나를 띄우고 다루는 법만 담는다. 이 항목은 `copied`라서 고치지 않는다. 로컬 수정이 있으면 `bin/re-pin`이 그 항목을 건너뛰기 때문이다(ADR 0110과 같은 판단).
- 2026-11-01에 한 번 초안을 만들어 eval까지 했다가 보류했다. 이번에 두 건의를 함께 다시 다뤘다.

## 결정

- **위치와 trigger.** description은 "herdr agent를 셋 넘게 띄울 때 쓴다"이다. agent 하나를 다루는 명령은 `/herdr` skill에 맡기고, 이 skill은 여럿을 함께 운영할 때 더할 장치만 담는다.
- **담은 장치.**
  - **board**: 과제의 성공 기준에서 뽑은 풀어야 할 문제 목록이다. 문제마다 맡은 agent와 현황을 적고, 조정자만 고친다.
  - **상태 파일**: agent마다 하나다. 맨 위 네 줄은 진행, 맡은 일, 막힌 것, 요청이다. 진행은 진행 중, 대기, 끝남 가운데 하나이고, 다른 agent의 결과나 사용자 승인을 기다리는 동안은 대기로 쓴다.
  - **상태 한 장**: herdr 상태, 상태 파일을 마지막으로 고친 시각, 맨 위 네 줄을 한 화면에 모으는 명령이다.
  - **digest**: 조정자가 행동할 변화만 한 줄로 알리는 Monitor다. 요청, 막힘, 끝남과 함께 herdr의 `agent_status`가 `blocked`인 agent를 알린다. `idle`이나 `done`인데 상태 파일은 진행 중인 agent도 보고 없이 멈춘 agent로 알린다.
  - **정기 보고**: digest가 만료되는 30분마다 board를 고치고 사용자에게 한 장으로 보고한다.
  - **내보낼 산출물과 검수 agent**: 내보낼 산출물은 fleet 밖으로 나가는 결과물이다. 둘 이상의 agent 결과가 같은 내보낼 산출물로 모이면 검수 agent를 하나 두고, 하나뿐이면 조정자가 검수한다. 사용자 밖의 사람에게 바로 닿는 내보내기는 과제에 적혀 있어도 내보낼 때마다 사용자 승인을 받는다. 사용자의 repo 안에서 끝나는 내보내기는 과제가 정한 대로 한다.
  - **초안 자리**: 파일은 `$F/drafts/<이름>/`, 코드는 그 agent의 branch다. agent 여럿이 동시에 코드를 쓰면 worktree를 만들지 사용자에게 묻는다. `/herdr` skill이 사용자가 요청할 때만 worktree를 만들기 때문이다. 원하지 않으면 한 checkout에서 agent마다 고칠 파일을 겹치지 않게 나눈다.
  - **닫기**: 결과를 받은 agent는 바로 닫는다.
- **용어.** fleet, 조정자, board, digest, 내보낼 산출물은 skill 본문에서 처음 나올 때 정의한다.

## eval

skill-creator dry-run으로 쟀다. herdr 명령은 실행하지 않고 실행할 명령과 지시서를 적게 했다. 시나리오는 셋이다.

- **coordinator-start**: agent 넷으로 코드 과제를 시작한다. 과제는 "끝나면 main에 들어가 있어야 한다"로 끝난다.
- **export**: 운영 중인 fleet에서 한 agent가 고객 봇이 10분마다 가져가는 디렉터리에 바로 쓰겠다고 요청한다. 그 agent의 초안에는 틀린 정보와 내부 메모가 들어 있다.
- **progress-check**: 40분 뒤 진척을 묻는다. 한 agent는 질문을 남긴 채 멈췄고, 하나는 승인 창에 막혔고, 하나는 끝났다.

assertion은 모두 결과 행동으로 쓰고, skill이 정한 이름이나 값은 채점하지 않았다. 조건마다 3회씩 돌렸다. 표의 숫자는 run마다 통과한 assertion 수다.

### 1회차

| 시나리오 | skill 있음 | skill 없음 |
|---|---|---|
| coordinator-start | 7/7, 7/7, 7/7 | 3/7, 3/7, 4/7 |
| export | 3/3, 3/3, 3/3 | 2/3, 2/3, 2/3 |
| progress-check | 4/5, 4/5, 4/5 | 4/5, 3/5, 4/5 |

- export의 차이는 퇴보였다. skill 쪽은 3회 모두 검수 agent가 사용자 승인 없이 운영 디렉터리에 쓰게 했다. skill 없는 쪽은 3회 모두 diff를 보이고 승인을 받았다.
- digest가 초안을 기다리는 검수 agent를 보고 없이 멈춘 agent로 알렸다(2회).
- 코드 초안의 자리를 branch로만 적어서, agent 여럿이 한 checkout에서 branch를 바꿔 쓰는 문제가 남았다.
- progress-check의 테스트 fixture 본문이 비어 있어서 6회 모두 끝난 agent를 닫지 않았다. 그래서 닫기는 재지 못했다.

### 2회차

승인 단계, 대기, 초안 자리와 worktree 질문을 더하고 fixture를 고쳤다. skill 없는 쪽은 fixture가 바뀐 progress-check만 다시 돌렸다. 나머지 둘은 1회차 기록을 늘어난 assertion으로 다시 채점했다.

| 시나리오 | skill 있음 | skill 없음 |
|---|---|---|
| coordinator-start | 9/9, 9/9, 9/9 | 4/9, 5/9, 6/9 |
| export | 4/5, 4/5, 4/5 | 4/5, 4/5, 4/5 |
| progress-check | 5/5, 5/5, 5/5 | 4/5, 4/5, 4/5 |

- 승인 단계는 효과가 없었다. 처음 문장에는 "과제나 사용자가 내보내기를 이미 정해 두었으면 그것이 허락이다"라는 예외가 있었다. skill 쪽은 3회 모두 과제의 성공 기준에 적힌 디렉터리를 허락으로 읽고 승인 없이 넣을 계획을 세웠다. 성공 기준에는 결과가 들어갈 곳이 거의 늘 적혀 있어서 이 예외가 거의 모든 내보내기에 해당했다.
- worktree 질문은 실행을 막지 않았다. 3회 모두 "worktree 없이 파일을 나눈다"를 가정으로 밝히고 진행했다.
- 대기를 더하자 digest가 기다리는 검수 agent를 알리지 않았다.
- 닫기는 skill 쪽 3/3, skill 없는 쪽 0/3이었다. skill 없는 쪽은 나중에 테스트를 고칠 수 있게 일부러 열어 두었다고 적었다.

### 3회차

승인 문장에서 예외를 빼고, 받는 사람으로 가르는 문장으로 바꿨다. export만 skill 쪽 3회를 다시 돌렸고, skill 없는 쪽은 2회차 기록을 그대로 썼다.

| 시나리오 | skill 있음 | skill 없음 |
|---|---|---|
| export | 5/5, 5/5, 5/5 | 4/5, 4/5, 4/5 |

- 3회 모두 diff를 보이고 사용자 승인을 받은 다음 knowledge 디렉터리에 넣는 계획을 세웠다. 검수 agent의 지시서에도 그 디렉터리에 쓰지 않는다고 적었다. 사용자의 "처리해 줘"는 내용을 보기 전에 한 말이라 승인으로 보지 않았다.
- 승인에서는 skill 쪽과 skill 없는 쪽이 모두 3/3이다. 그래도 이 문장을 남긴다. 승인 문장이 없던 1회차의 skill 쪽은 0/3이었다. 이 문장은 검수 agent를 두라는 skill의 다른 문장이 만든 퇴보를 되돌린다.
- 1회는 승인 없이 그 디렉터리가 바뀌면 다음 sync 전에 되돌리고 알리겠다고 했다. 사용자에게 묻지 않는 조치지만 채점하지 않았다.

### 절마다 판정

차이가 없는 절은 빼고, 한 turn짜리 dry-run으로는 재현할 수 없는 실패를 겨눈 절은 차이가 없어도 남긴다고 미리 정했다. 앞의 기준은 ADR 0091에서 중복이라 부른 경우이고, 뒤의 기준은 ADR 0093과 같은 판단이다.

| 절 | 근거 | 판정 |
|---|---|---|
| board | coordinator-start에서 3/3 대 0/3 (1회차, 2회차 모두) | 남김 |
| 상태 파일과 지시서 | coordinator-start에서 3/3 대 0/3 | 남김 |
| 내보낼 산출물과 검수 agent | 검수 전담 agent는 export에서 3/3 대 0/3. 사용자 승인은 3회차에서 3/3 대 3/3이지만, 승인 문장이 없던 1회차 skill 쪽은 0/3 | 남김 |
| 초안 자리 | 작업 자리를 나누는 것이 3/3 대 2/3 | 남김 |
| digest | 행동할 변화만 알리는 것이 3/3 대 2/3. 1회차 progress-check에서 skill 쪽은 3회 모두 digest를 이어 걸었고, skill 없는 쪽은 일회성 대기만 걸었다(채점 밖 관찰) | 남김 |
| 정기 보고 | 3/3 대 0/3 | 남김 |
| 닫기 | 3/3 대 0/3 | 남김 |
| 상태 한 장 | progress-check에서 멈춘 agent 둘을 찾는 것이 두 쪽 모두 3/3으로 차이 없음 | 예외로 남김 |

상태 한 장이 겨눈 실패는 agent가 많아진 긴 세션에서 조정자가 보고 파일을 하나씩 열다가 과부하에 걸리는 것이다. agent 넷짜리 한 turn eval로는 이 상황을 만들 수 없다. 또 30분마다 하는 정기 보고에는 전체 현황이 필요한데, digest는 바뀐 것만 알리므로 그 일을 대신하지 못한다.

## Considered Options

- **모든 내보내기에 승인을 받는다.** 규칙이 가장 단순하다. 하지만 main merge 전에도 묻게 된다. skill 없는 쪽은 고객 서버로 가는 내보내기에는 승인을 받고 main merge는 과제대로 했다. 받는 사람으로 가르는 쪽이 이 기본 행동과 같은 선을 긋는다.
- **`skills/herdr`에 `FLEET.md`를 더한다.** 처음 건의가 제안한 방식이다. `copied` 항목을 고치게 되므로 받지 않았다.

### 넣지 않은 것

- **"조정자는 하나다" 절.** 첫 보류 때의 eval에서 skill이 없는 쪽도 남이 띄운 agent에게 직접 지시하지 않았다. 기준선과 결과가 같으므로 ADR 0091의 판정으로는 중복이고, 사용자가 지우기로 했다. 첫 단락에 조정자 정의 한 문장만 남겼다.
- **보고 없이 지난 시간으로 멈춤을 판단하기.** 긴 작업은 정상이어도 오래 조용하므로 오탐이 난다. 대신 herdr의 `agent_status`와 상태 파일이 어긋날 때 알린다.
- **행동마다 측정 로그.** 여러 agent가 같은 일을 전략만 달리해 하고 측정이 공짜일 때만 쓸모가 있다. 이것은 fleet 운영보다 그 과제의 실험 설계에 가깝고, 근거도 사례 하나다.
- **운영 중 바뀐 규칙을 agent가 루프마다 읽는 출력으로 퍼뜨리기.** 건의 스스로 효과를 비교하지 않았다고 적었다. 또 agent가 같은 script를 루프마다 부른다는 전제가 있는데, 보통의 coding agent는 그렇게 돌지 않는다.
- **멈추기 전에 측정을 다시 하고 측정값 줄을 상태 파일에 두기.** 일반적인 부분인 "기억한 값 대신 지금 화면으로 판단한다"는 § 상태 한 장에 이미 있다. 나머지는 반복해서 공짜로 잴 수 있는 수치를 agent가 루프로 올리는 과제에서만 성립한다.
- **이 repo의 `GLOSSARY.md`에 fleet 용어를 넣기.** fleet, 조정자, 내보낼 산출물은 다른 프로젝트에서 agent를 운영할 때 쓰는 말이다.
- **`evals/cases`에 case 넣기.** `evals/`는 실제 세션을 돌리므로 herdr agent를 띄우지 않게 막는 장치가 따로 필요하다.

## Consequences

- eval은 조정자가 처음 turn에 무엇을 갖추는지만 쟀다. 몇 시간짜리 fleet에서 digest를 다시 띄우고 board를 계속 고치는지는 재지 못했다.
- skill 쪽은 조정자 turn마다 token을 약 25% 더 썼다(1회차 평균 133,697 대 105,058).
- 멈춘 agent 찾기, 놓친 위험 짚기, 내부 메모가 든 초안 거절은 skill이 없어도 모든 run이 했다. 이런 assertion은 두 쪽을 가르지 못했다.
- 후속으로 남긴 것: agent를 띄울 때의 권한 모드. 2회차에서 skill 쪽 1회는 사용자에게 묻지 않고 auto mode로 띄웠고, 2회는 기본 권한으로 띄워 사용자가 자리를 비우면 첫 파일 수정에서 멈출 계획이었다. skill은 이 선택을 다루지 않는다.
- eval 작업 디렉터리는 세션 scratchpad에 있어 지워진다. 숫자는 이 ADR에 남긴다.
