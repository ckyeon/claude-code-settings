# 0133 — transcribe.py가 대기 시각 없는 429에서 기다리고, 끝낸 청크를 캐시에 남긴다

`transcribe.py`의 rate limit 재시도와 청크 처리를 고쳤다. 분당 한도의 429가 대기 시각을 주지 않으면 60초를 기다린 뒤 다시 보낸다. 끝낸 청크의 응답은 `~/.cache/transcribe/`에 남기고, 같은 명령을 다시 실행하면 그 청크는 요청하지 않는다.

## 경위

- 다른 프로젝트의 세션이 inbox에 남긴 건의(ADR 0098)에서 왔다. 99분 녹음의 둘째 청크에서 429가 나자 스크립트가 바로 끝났고, 끝낸 첫 청크의 결과도 남지 않았다.
- 그 429 본문은 "Rate limit exceeded ... (limit: 10000 input tokens per minute on Tier 1). Please retry later ..."였다. `_retry_delay_s`는 `[Rr]etry in ([0-9.]+)s`만 찾았으므로 None을 돌려줬고, `_retrying`은 재시도할 수 없는 오류로 보고 올렸다.
- `transcribe()`는 청크 결과를 메모리에 모았다가 끝에 한 번 썼고, 잘라 낸 청크 파일도 임시 디렉터리에 있었다. 그래서 어느 청크에서든 예외가 나면 그때까지 끝낸 청크가 모두 사라졌다. 2026-11-01에도 끝 11초 청크가 본문 없이 돌아와 앞 두 청크를 함께 잃었다.

## 결정

- **대기 지시를 Go duration 표기로 읽는다.** "retry in 1m5s"와 "retry in 12h7m46s" 같은 시와 분 표기도 초로 바꾼다. 하루 한도 응답은 "Please retry in 12h7m46s"였다.
- **지시가 120초보다 길면 기다리지 않고 끝낸다.** 전에는 `min(delay + 2, 120)`이었다. 시와 분 표기를 읽게만 바꾸면, 하루 한도에서 120초씩 네 번 기다린 뒤 똑같이 실패한다.
- **캐시는 `--out` 옆이 아니라 `~/.cache/transcribe/<원본 이름>-<key>/`에 둔다.** 건의는 `--out` 옆의 작업 디렉터리를 제안했다. 그런데 실패한 실행은 `--out` 없이 stdout으로 받았으므로, `--out` 옆에 두면 이 사례를 막지 못한다. key는 원본 파일의 경로, 크기, mtime과 모델, 청크 길이, 요청 설정을 묶은 hash다. 옵션을 바꿔 다시 돌리면 다른 디렉터리를 쓰므로 다른 설정의 응답이 섞이지 않는다.
- **텍스트가 아니라 응답 JSON을 저장한다.** 앵커 모드와 화자 구분 모드는 응답의 word 주석에서 시각과 화자를 다시 계산한다. 개발용 `dump_dir`도 같은 JSON을 저장한다.
- 모두 끝나면 캐시를 지운다. 실패하면 오류 메시지 뒤에 끝낸 청크 수와 캐시 경로를 붙여, 같은 명령을 다시 실행하면 된다고 알린다.

## Consequences

- 확인은 scratch에서 했다. 파싱은 건의에 실린 429 본문 셋(분당 한도의 "Please retry later", "retry in 56.3s", 하루 한도의 "12h7m46s")과 직접 만든 예 둘("1m5s", "593.591975ms")로 확인했다. 그다음 API 호출을 가짜로 바꿔 둘째 청크 실패, 다시 실행해 첫 청크 건너뛰기, 캐시 삭제, 앵커 모드의 시각 오프셋을 확인했다. 실제 API로는 돌리지 않았다. `tests/`에는 transcribe 테스트가 없어서 repo 테스트는 더하지 않았다.
- 재시도는 여전히 최대 네 번이다. 같은 project의 한도를 여러 실행이 나눠 쓰면 네 번 안에 통과하지 못할 수 있다. 그때도 끝낸 청크는 남으므로 다시 실행하면 이어진다.
- 끝 청크가 본문 없이 돌아오는 문제는 그대로다. 다시 실행해도 같은 청크에서 다시 실패한다. 후속 과제로 남긴다.
